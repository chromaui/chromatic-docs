# How preferMergedBaselines Works?

`preferMergedBaselines` is a Chromatic feature flag that changes how baseline selection works. When a build has multiple ancestor builds, Chromatic has to choose which baseline to use for each story. By default, it picks the most recently accepted snapshot.

If you enable the preferMergedBaselines flag, Chromatic switches to preferring the “incoming” baselines from other branches, such as main, so you don't have to re-accept changes that were already approved elsewhere.

This is especially useful when your team merges or rebases branches against main. Without the flag, Chromatic can fall back to a stale baseline from the same branch, which can make approved changes from main appear as new diffs. With the flag enabled, Chromatic can pick the fresher main baseline instead.

**Important things to know:**

- `preferMergedBaselines` is an account-level feature flag. It applies to all projects under the account, not just a single project.
- It can't be enabled via a CLI flag and must be turned on by the Chromatic team on your behalf. To request it, email support or message them via chat.
- It helps when developers are re-accepting changes that were already approved on another branch after a rebase or merge.
- It is most useful in parallel development workflows where multiple branches are merged into main, and you want feature branches to pick up the latest approved main baseline.
- It only takes effect when there is a merge commit with multiple parents. If you use `git rebase` rather than `git merge`, Chromatic cannot see main as an ancestor, so the flag has no effect.

## Workflows

1. **High-frequency trunk-based development with long-lived PRs**

In active teams, `main` updates rapidly while a developer works on a multi-day feature branch. Other developers merge and accept updates to shared components (e.g., updating a global `Button` design) on `main`. When you run `git merge main` into your feature branch, Chromatic's default behavior compares your branch against its own previous snapshot on that branch. This forces you to re-approve the global Button changes—even though someone else already vetted and approved them on `main`.

**With `preferMergedBaselines`:** Chromatic detects the merge commit, evaluates both parent histories, and pulls the newly approved `Button` baseline directly from `main`. So, you don't need to reapprove these changes and only review visual diffs unique to your branch.

```{mermaid}
main:    A ---> B (Accepted global UI change)
            \      \
  feature:   C ----> M (Merge commit)
```

2. **Integration and release branches**

Enterprise workflows often use intermediate integration branches (e.g., `release/v2.1` or `staging`) before hitting production (`main`). Bug fixes and component updates are often merged directly into `staging` or `release/v2.1` and approved there. When developers sync their feature branches with `staging` (`git merge staging`), Chromatic would normally pull the old feature branch snapshot as the baseline.

**With `preferMergedBaselines`**: The system prioritizes the accepted snapshots coming in from the target integration branch (`staging`), ensuring features inherit pre-approved bug fixes immediately.

3. **Parallel feature branches sharing base components**

Two feature branches (`feature-A` and `feature-B`) are developed in parallel. `feature-A` completes first, updates shared design tokens, and merges into `main`. Developer B pulls `main` into `feature-B` (`git merge main`). Without the flag, Developer B is forced to re-verify Developer A's design token changes because Chromatic defaults to `feature-B`'s older snapshot. This causes confusion when Developer B lacks context on Developer A's changes.

**With `preferMergedBaselines`**: Chromatic prioritizes `main`'s incoming baseline over `feature-B`'s historical baseline, bypassing redundant reviews.

## Limitations and considerations

1. Commits and branches must still be in the git history for them to be picked up.
2. The flag uses the baseline at the last sync point from main, not main's current `HEAD`. If your branch is significantly behind main, you need to merge or rebase before the flag produces the expected result.
3. `preferMergedBaselines` is account-wide — there is no way to enable it for a single project while leaving others on default behavior.
